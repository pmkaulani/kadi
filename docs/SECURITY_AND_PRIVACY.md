# KADI — Security, Privacy & Kenya Compliance Specification

## 1. Regulatory Context: Kenya Data Protection Act, 2019 (KDPA)
Kadi is built primarily for the Kenyan market, subject to the **Kenya Data Protection Act, 2019** and the guidance of the **Office of the Data Protection Commissioner (ODPC)**.

### 1.1 Lawful Basis & Purpose Limitation
- **Guest Contacts:** Guest phone numbers and email addresses provided by hosts are processed solely for the legitimate interest and specific purpose of delivering the event invitation and RSVP updates.
- **Explicit Consent for Automated Messaging:** Phone numbers uploaded into Kadi CANNOT be used for automated WhatsApp marketing or unsolicited platform notifications without explicit, affirmative opt-in records.
- **Children's Data:** For baby showers, baptisms, first communions, and children's birthdays, the platform strictly minimizes data collection regarding minors. No direct profiling, public indexing, or identifiable images of minors may be shared without parental/guardian consent.

### 1.2 Data Subject Rights
The platform implements automated workflows for data subjects:
1. **Right of Access / Export:** Hosts and guests can request a machine-readable export (JSON/CSV) of all personal data held.
2. **Right to Rectification:** Guests can update their RSVP, contact details, and dietary requirements.
3. **Right to Erasure ("Right to be Forgotten"):** Hosts can permanently delete events, guest records, and media. Expired guest tokens and inactive contact records follow a defined retention schedule.

## 2. Security Controls & Architecture

### 2.1 Authentication & Session Management
- Passwords are never stored in plaintext (Argon2id or bcrypt with strong work factor).
- Managed identity sessions utilize `HttpOnly`, `SameSite=Lax`, and `Secure` cookies.
- Brute-force protection on authentication and token verification routes (sliding window rate limiting).

### 2.2 Guest Token Security
- Guest invitations use high-entropy cryptographic tokens (minimum 256 bits of entropy, base64url encoded).
- Private invitation tokens are **hashed before storage** in the database (SHA-256) where practical to prevent leakages via database dumps.
- Guest tokens are strictly **excluded from client-side analytics**, server access logs, and third-party tracking scripts.
- Tokens can be instantly revoked or regenerated by the host from the dashboard.

### 2.3 Financial & Ledger Integrity
- Kadi separates guest contributions from platform subscription billing.
- All payment transactions use append-only ledgers. Financial history is never destructively updated or deleted.
- M-Pesa Daraja callback validation enforces strict verification of Originating ShortCode, Amount, Transaction ID, and Request ID.
- Webhook endpoints are strictly idempotent and defend against replay attacks.

### 2.4 Upload & Media Security
- All file uploads are validated for MIME type, file magic numbers, and size limits before processing.
- Direct uploads use short-lived presigned URLs.
- User-supplied image filenames are stripped and randomized with UUIDs to prevent directory traversal and metadata leaks.

## 3. Data Retention Schedule

| Data Category | Retention Period | Deletion Mechanism |
|---|---|---|
| Active Event Data | Duration of event + 90 days | Host prompt to archive or delete |
| Archived Events | 1 year after event date | Automatic soft-delete with 30-day purge window |
| Guest Tokens | Event date + 30 days | Cryptographic invalidation |
| M-Pesa / Financial Logs | 7 years (statutory tax requirement) | Read-only encrypted cold storage |
| Communication Logs & Audit Trails | 180 days | Rolling partition pruning |
